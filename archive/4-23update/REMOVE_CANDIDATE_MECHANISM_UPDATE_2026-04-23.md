# 4-23 更新记录：移除当前候选枚举机制

日期：2026-04-23

## 目的

当前控制链里的候选机制主要依赖离散参数枚举：

- 控制层枚举多个观察位姿
- 执行器再对输入目标做局部候选扰动

这套做法存在几个明显问题：

1. 不是从任务约束出发，而是在连续空间里做少量拍脑袋式离散取样
2. 没有真正利用机械臂工作空间、可达性或场景碰撞信息
3. 容易让系统行为变得不可解释，且对桌面等环境约束不敏感
4. 代码量膨胀，反而不利于后续引入新的、明确建模的策略

因此本轮先做一件事：

> 把当前复杂候选机制从运行链路中拿掉，只保留最原始的单目标位姿接受与发布机制。

## 本次修改

### 1. 简化 `arm_pose_controller.py`

文件：

- `src/vision_arm_control/vision_arm_control/arm_pose_controller.py`

处理方式：

1. 删除 `PoseArray` 候选发布
2. 删除候选生成、候选排序、离散横向偏移、离散 standoff 偏移等逻辑
3. 删除对 `selected_semantics` 的依赖
4. 保留最小主链路：
   - 接收 `/target_id`
   - 接收 `/cylinder_pose_base`
   - 根据圆柱中心与轴向直接生成单个目标相机位姿
   - 通过手眼标定换算为单个末端位姿
   - 发布到 `/target_pose` 和 `/target_pose_stamped`

当前保留的几何动作只有：

- `camera_standoff_m`
- `look_at_depth_m`
- `axis_into_tube_sign`（仅在无法从当前相机所在侧自动判定时作为 fallback）

也就是说，控制层现在只做“接受一个目标位姿并发布一个目标位姿”。

### 2. 执行器切回单目标输入模式

文件：

- `src/control/config/vision_moveit_executor.params.yaml`

处理：

1. `prefer_pose_array: false`
2. `enable_feasible_pose_projection: false`
3. `max_candidate_plan_tries: 1`
4. `candidate_batch_max_count: 1`

这意味着当前执行器运行时不再优先等待 `/target_pose_candidates`，也不再对收到的目标做局部候选扩展。

## 当前链路

现在的有效路径变成：

1. 视觉层发布已选中目标的 `/vision/cylinder_pose`
2. 转换层发布 `/cylinder_pose_base`
3. 控制层直接生成一个目标末端位姿
4. 执行器直接消费单个 `/target_pose_stamped`

## 保留但未删除的内容

本轮重点是“从运行链路拿掉候选机制”，不是彻底重构全部历史代码，因此：

1. 执行器 C++ 内部的候选相关实现仍在代码里
2. 但当前参数已将其关闭

如果后续确认不再需要，可以再做一次纯清理型重构，把执行器里的候选分支和对应参数也从源码层面删除。

## 结果

这一轮之后，系统回到了一个更适合作为“新策略基底”的状态：

- 输入明确
- 输出单一
- 行为可解释
- 控制层代码显著缩短

接下来如果要设计新策略，建议直接围绕以下问题建模：

1. 给定圆柱中心与轴向，什么样的观察位姿在任务上是合理的
2. 这个观察位姿如何约束在机械臂真实可达工作空间内
3. 如何把可达性/碰撞/场景先验显式纳入，而不是再退回离散枚举
